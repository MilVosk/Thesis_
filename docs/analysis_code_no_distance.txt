Add NA few-shots that are literal copies of the Helper dictionary, GIS/resource listings, and regulation blurbs so the model learns that schema documentation and catalog metadata should not yield HAVE/OCCUR_IN.
Supply HAVE positives phrased as definitions/measurement notes (crown ratio formula, OTU descriptions) plus OCCUR_IN positives that look like Austin/Gutianshan catalog text to teach the model that those patterns are valid relations.
Include INFLUENCE few-shots that emphasize comparative likelihood or hypothesized effects (“more likely to show vulnerability”, “threatens ecosystems”, “depends on dissolved matter”) so probabilistic phrasing doesn’t default to NA while also discouraging weather abstract hallucinations.


Across 0-shot and the few-shot variants (1/2/2, 2/4/3, 2/4/4, 4/8/8), the error profile barely changes: every configuration hallucinates HAVE on the “Helper (comment Karin)” schema text and other dataset summaries, fires INFLUENCE whenever “influence/affect” appears in the repeated weather–fungi abstract, and treats long catalog/protocol prose as OCCUR_IN even without a concrete occurrence. Conversely, real relations buried inside those same metadata-style passages are almost always missed: definition/measurement sentences drop HAVE, regulatory or GIS catalog text drops OCCUR_IN, and probabilistic “more likely/threatens” phrasing drops INFLUENCE. Increasing few-shot counts does not solve this; it just inflates INFLUENCE false positives (e.g., 20 at 2/4/4) while recall gaps persist (≈50 FN per run, dominated by 40–50% HAVE).

To break the loop you need targeted prompt edits, not more examples: (1) add NA few-shots lifted directly from the Helper dictionary, GIS/resource listings, regulation blurbs, and protocol paragraphs so the model stops labeling documentation as HAVE/OCCUR_IN/INFLUENCE; (2) explicitly validate the label list to block malformed tags like OCCURIN; (3) seed positive few-shots that mirror the hard cases—definition/measurement prose for HAVE, catalogue metadata for OCCUR_IN, and comparative/probabilistic statements (“more likely,” “threatens,” “depends on”) for INFLUENCE. Without those contrastive templates the classifier keeps confusing schema text for facts and ignores real relations hidden in documentation-style wording, regardless of shot count. Final analysis:
Result Comparison

Natural prompts lead multi-class accuracy across every shared shot setting: e.g., 2/4/4 averages 0.5743 multi-class F1 vs. the code prompt’s 0.4872 at the same setting (evaluation_average.csv (line 5), evaluation_average.csv (line 10)). Even the best code run (2/4/3 at 0.4897) trails natural setups like 2/4/3 (0.5411) and 4/8/8 (0.5641) (evaluation_average.csv (line 4), evaluation_average.csv (line 9), evaluation_average.csv (line 11)).
Code prompts trade that recall for slightly better binary scores: the 4/8/8 code run tops the table with 0.6391 binary F1 and 0.2325 hamming loss, edging the strongest natural binary score of 0.6363/0.2392 at 2/4/4 (evaluation_average.csv (line 6), evaluation_average.csv (line 10)).
Error totals reflect the same pattern. At zero-shot, the code prompt produces fewer false positives (44 vs. 55) but more false negatives (88 vs. 84) compared with the natural instructions, indicating higher precision but worse coverage (fp_fn_comparison.csv (line 2), fp_fn_comparison.csv (line 3)).
For 2/4/4, natural prompting again keeps both FP and FN counts lower (49 FP, 46 FN) than the code prompt (52 FP, 49 FN), aligning with the higher multi-class F1 on that configuration (fp_fn_comparison.csv (line 6), fp_fn_comparison.csv (line 9)).
The 4/8/8 pair shows similar precision/recall trade-offs: code reduces false positives to 45 but lets false negatives match natural (49 vs. natural’s 48), while natural accrues more OCCUR_IN mistakes but balances the classes (fp_fn_comparison.csv (line 7), fp_fn_comparison.csv (line 10)).
Code outputs also contain invalid OCCURIN labels in every configuration (1–4 per run), whereas natural prompts never emit out-of-set tags, highlighting an additional accuracy issue in the code results themselves (fp_fn_comparison.csv (line 4), fp_fn_comparison.csv (lines 6-7)).
Overall, the natural-language prompt produces better balanced predictions and higher multi-class F1, while the code prompt favors precision over recall and suffers from the extra invalid label emissions. If you want better coverage per class, stick with the natural prompt; if you need higher binary precision and can tolerate more misses (and fix the label validation), the code prompt can be useful.
